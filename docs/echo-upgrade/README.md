## 检测即点击（架构约定）

所有按钮（**培养 / 阶段放入 / 强化 / 排序 / 弹窗**）均通过 OCR 检测其文字框，再点
「检测到的框中心」（`_click_text` → `click_box`），**不再依赖精确点击坐标**。每个按钮
只保留一个「大致搜索区域」常量，按钮落在该区域内即可命中，游戏版本微调布局不会失效。

- 搜索区域（只需覆盖按钮大致位置）：`TRAIN_BTN_BOX` / `ADD_MAT_BOX` / `CONFIRM_BOX` /
  `DIALOG_BOX` / `SHORTAGE_BOX` / `SORT_BTN`
- 仅有的固定点击点：`FIRST_SLOT`（列表首格，图标类 UI 无稳定文字标签）
- 仅有的精确标定项：`DETAIL_LEVEL_BOX` / `PREVIEW_LEVEL_BOX`（等级数字需排除分母，必须精确圈定）

## 单步调试与截图日志

`run()` 顶部「调试入口」配置（下拉）决定执行范围，支持把流程拆开单独测试：

| 调试入口 | 前提假设 | 执行的步骤 | 典型用途 |
|---|---|---|---|
| 完整流程 | 自动开背包并循环 | 选择→读等级→进面板→投料→强化→查资源→返回→复核→排序 | 正式跑 |
| 仅选择声骸 | 已在背包声骸页 | 选首格 + 读等级 | 验证列表/排序/读等级 |
| 仅升级(从进入面板) | 已选中声骸在背包页 | 进面板→投料→强化→查资源→返回→复核 | 验证进面板与投料逻辑 |
| **仅升级(已在面板)** | **游戏正停在强化面板** | 投料→强化→查资源→返回→复核 | **升级失败就地重测，不必重跑全流程** |
| 仅返回声骸选择 | 在面板或背包 | 返回背包 + 排序回顶部 | 验证退出/排序 |
| 单步暂停调试 | 同完整流程 | 每步前暂停，可 [回车]继续 / [s]跳过 / [q]退出 | 像调试器一样逐帧走查 |

任一子步骤失败即**停在当场**（不回滚、不强行继续），方便直接观察现场。
每步保存带检测框标注的截图（`logs/echo_upgrade/<运行时间>/<序号>_<步骤>.png`）与
结构化执行日志（`steps.jsonl`、`report.json`）。日志目录可在「截图日志目录」配置。

> 实机标定前 `CALIBRATED=False`，`run()` 仍直接拒绝执行，不会误投料。

> 实现代码已落地到 `ok-ww/ok-wuthering-waves-master/src/task/UpgradeEchoTask.py`
> 并在 `config.py` 的 `onetime_tasks` 中注册（echo-only 分支上的唯一任务）。
> 本文档描述的仍是阶段 0 的方案基线，代码已按 `05-评审记录/评审记录.md`
> 的 2026-11-07 走查记录修正，功能验收后统一回填各模块文档。

## 文档规范

每份功能文档必须包含以下章节（缺一不可）：

| 章节 | 说明 |
|---|---|
| **目标** | 该模块要解决什么问题、达成什么效果 |
| **范围** | 明确的边界：做什么、**不做什么**（In/Out of scope） |
| **关键决策** | 为什么这么设计、否决过哪些备选方案及原因 |
| **依赖关系** | 依赖哪些其他模块/外部条件（游戏内设置、标定数据等） |
| **待办事项** | 未完成项、已知问题、需要标定的 TODO |

## 维护纪律

1. **先改文档，再改代码**（或至少同步提交）：功能调整前，先在对应模块文档的「关键决策」或「待办」里记录变更意图。
2. **每次代码改动 → 更新对应模块文档**：包括改了哪个方法的逻辑、为什么改、对验收标准的影响。
3. **进度更新到 `02-开发计划` 的看板**：阶段状态用 `[ ]`/`[x]` 或状态标记，完成后回填日期与结论。
4. **评审/测试发现的问题 → 记入 `05-评审记录` 和 `04-测试计划`**：闭环到「已修复」才算完结。
