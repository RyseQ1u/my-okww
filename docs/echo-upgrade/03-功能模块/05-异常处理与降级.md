# 功能模块 05：异常处理与降级

> 关联代码：`UpgradeEchoTask` 的 `process_one` 返回码 / `run` 主循环 / `summary` / `is_material_shortage` / `handle_dialogs`

## 目标

对所有可预见的异常分类处理，遵循"只有环境不可用才终止；资源不足/单件失败一律降级继续或优雅结束"。

## 范围

**In scope**：材料/贝币不足、等级 OCR 失败、强化未达预期、弹窗干扰、单件超时、连续异常、UI 改版。

**Out of scope**：账号封禁等游戏侧不可控风险（仅提示）。

## 关键决策

1. **返回码协议**：`process_one` 返回 `done`（完成）/ `skip`（跳过：已达标或无法处理）/ `fail`（失败：异常或强化未达预期）/ `no_material`（材料耗尽）。主循环据此统计并决定终止。
2. **材料不足 = 正常结束**：`no_material` 触发 `stop_reason = "材料或贝币不足"`，`summary()` 统计"完成 N / 失败 M / 跳过 K"后 `notify=True` 通知，按配置 `材料耗尽时暂停` 决定是否 `pause()`。**不抛异常**。
3. **贝币不足**：`is_material_shortage()` 用 `NOT_ENOUGH_RE = r"(不足|材料|贝币)"` 匹配弹窗；命中后**不点确认**（避免误消耗），走材料不足分支。
4. **连续异常保护**：`MAX_RETRY = 3`，`fail_count` 连续累计且等于总处理数时（`fail_count == done_count + fail_count`）判定"连续失败过多"终止，防死循环。
   - ⚠️ **风险（待验证）**：该条件 `self.fail_count == self.done_count + self.fail_count` 恒等于"没有成功过"，逻辑上等价于 `done_count == 0`，但表达晦涩，且 `fail` 与 `skip` 混在统计里可能漏判。见待办。
5. **单件超时**：`单件超时(秒)` 默认 90，主循环 `time.time() - t0 > timeout` 时记日志。但当前**超时后未真正中断该件**（仅打日志），需在 `process_one` 内做超时中断或依赖外层 `fail`。
6. **单件异常兜底**：`run` 用 `try/except` 包住 `process_one`，异常降级为 `fail`，保证一件失败不拖垮整个任务。
