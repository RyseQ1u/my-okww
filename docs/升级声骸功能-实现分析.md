## 0. 结论速览

| 维度 | 结论 |
|---|---|
| 设计思路 | 清晰且成立：把「预筛 + 等级升序」的列表当作自动前进的队列，无状态文件即可断点续跑 |

## 1. 功能定位与核心不变量

**目标**：用户先在游戏内筛好待升级声骸、按**等级升序**排序；程序逐件把首格声骸强化到运行期指定的目标等级 x。

**核心不变量（"列表即队列"）**：

```
排序后首格 = 当前最低等级的待处理件
强化一件 → 它的等级升高 → 自动排到队尾
→ 首格自然变成下一件，无需识别"这是哪件"、无需滚动、无需状态文件
```

这个不变量是整套设计的支点，也是"断点续跑"（中途停止 → 补材料 → 再点开始）能成立的原因。代价是**强依赖用户的前置操作**：筛选、升序、语言、热键，任一不满足，队列语义立即失效。

**明确不做**：副词条/双爆判定与弃置（那是 `EnhanceEchoTask` 的能力）、同步调谐、精确退料、经验表、多账号、多语言。

## 2. 核心逻辑：一个队列状态机 + 三层单件闭环

### 2.1 返回码协议（模块间唯一的"接口"）

`process_one(target)` 返回 4 种结果，主循环据此统计与决定终止：

| 返回码 | 含义 | 触发点 | 主循环行为 |
|---|---|---|---|
| `done` | 达标并完成复核 | 复核等级 ≥ x | `done_count += 1` |
| `skip` | 已达标 / 无法处理 | 首格选中失败、已达标、强化页未就绪 | `skip_count += 1`（**不计入循环上限**） |
| `fail` | 单件异常或复核未达标 | 抛异常、找不到强化按钮、复核 < x | `fail_count += 1`，可能触发保护 |
| `no_material` | 资源耗尽 | 「阶段放入」消失 / 命中不足弹窗 | 统计后终止 |

### 2.2 单件三层闭环

1. **投料闭环**：`enhance_to()` 反复点「阶段放入」→ 读**预览等级** → `preview >= x` 即停，最多 `MAX_BATCH = 8` 轮。这是"预览即真值"策略（方案决策 2 层级 A），不依赖经验表。
2. **强化闭环**：`confirm_enhance()` 点「强化」→ `handle_dialogs()` 清弹窗 → `read_level()` 读**详情等级**复核；若 `< x` 则补投一次再复核。
3. **队列推进闭环**：`back_to_list()` → `back_to_list_top()`（点排序两次，防御 3.7 版本"回列表自动选中刚强化件"）→ `select_first_echo()` → 读首格等级 → 判定是否全部完成。

三层各自独立读等级，本质是**用 OCR 观测替代状态机状态**：程序不维护"我在哪个界面"，每次都重新看画面推断。这让断点续跑很自然，但也让每个探针的正确性都变成致命依赖。

## 3. 执行流程（按代码实际路径）

### 3.1 `run()` 主流程

```
1. 读配置：target=int(目标等级) / limit=int(最大处理数量=200) / timeout=int(单件超时=90)
2. info_set：目标等级、已完成=0、已失败=0
3. ensure_main()                         回到游戏主界面
4. send_key("Bag Key"/"b")               打开背包，等 1.5s
5. if not in_echo_detail():              前置校验（"培养"按钮不存在 → 报错 notify 并 return）
6. while done_count + fail_count < limit:
     6.1 t0 = now()
     6.2 result = process_one(target)    try/except 兜底为 fail
     6.3 if now-t0 > timeout: 仅记一条 warning（不中断）
     6.4 统计 done/fail/skip；fail 时检查连续失败保护
     6.5 back_to_list()  →  back_to_list_top()
     6.6 select_first_echo()  →  level = read_level(DETAIL_LEVEL_BOX)
     6.7 终止判定（顺序敏感）：
         a) level is None        → "无法读取等级"，break
         b) level >= target      → "全部达到目标等级"，break
         c) result == no_material → "材料或贝币不足"，break
7. summary()  统计 + notify + 按配置 pause()
```

### 3.2 `process_one(target)` 单件流程

```
1. if not in_echo_detail(): 若 select_first_echo() 也失败 → skip
2. level = read_level(DETAIL_LEVEL_BOX, retries=3)
3. if level is not None and level >= target → skip
4. if not confirm_enhance_available()        → skip
   ┌── 这里应该有「点击培养进入强化面板」，但代码里没有 ──┐
5. status, preview = enhance_to(target)      循环投料
6. if status == no_material:  is_material_shortage() 二次确认后 → no_material
7. if not confirm_enhance():                 → fail
8. handle_dialogs()                          清弹窗
9. new_level = read_level(DETAIL_LEVEL_BOX)  复核
10. if new_level is not None and new_level < target:
       补投一次 enhance_to + confirm_enhance + handle_dialogs + 再读
11. if new_level >= target: 可选按 c 上锁 → done；否则 → fail
```

### 3.3 关键状态转移

游戏里其实只有**两个界面**，不是方案文档假定的"列表页 / 详情页 / 强化页"三层：

| 界面 | 可见标志 | 参考实现用法 |
|---|---|---|
| 背包声骸页（网格 + 选中件详情） | 「培养」按钮 | `EnhanceEchoTask.esc()` 反复 ESC **直到「培养」出现**，即把它当"已回到背包页"的标志 |
| 强化/培养面板 | 「阶段放入」「强化」 | `find_add_mat()` / `wait_click_ocr(..., '强化并调谐')` |

**因此 `in_echo_detail()` 探到「培养」= 在背包页，而不是"在详情页"。** 这个语义错位直接导致第 6 节的 G2。

## 4. 关键数据处理

### 4.1 归一化坐标 → 像素框

类常量全部是 `(x1, y1, x2, y2)` 的 0~1 归一化值，基于 16:9：

```
TRAIN_BTN_BOX   (0.82,0.86,0.97,0.96)   培养按钮 / 背包页探针
DETAIL_LEVEL_BOX(0.09,0.10,0.40,0.20)   详情等级
PREVIEW_LEVEL_BOX(0.09,0.10,0.40,0.20)  预览等级  ← 与上一行相同
ADD_MAT_BOX     (0.09,0.60,0.38,0.86)   阶段放入
CONFIRM_BOX     (0.10,0.88,0.29,0.96)   强化按钮
DIALOG_BOX      (0.24,0.18,0.75,0.98)   弹窗区（覆盖了大半屏）
FIRST_SLOT      (0.13,0.21)              列表首格
SORT_BTN        (0.35,0.917)             排序按钮
```

框架 `ocr(x,y,to_x,to_y)` 内部用 `relative_box(frame_width, frame_height, ...)` 换算成像素裁剪区；`click(x,y)` 中 `0<x<1` 会自动代理到 `click_relative`。所以坐标可直接复用，也意味着**非 16:9 分辨率（21:9 带鱼屏、4:3）会整体偏移**。

其中 6 个（TRAIN / CONFIRM / ADD_MAT / DIALOG / FIRST_SLOT / SORT）与 `EnhanceEchoTask` 中已跑通的数值逐一对得上，不是占位值 —— 详见 `docs/项目分析-2026-11-07.md` 第三节。

### 4.2 OCR → `Box` → 文本匹配

`ocr()` 返回 `list[Box]`，每个 `Box` 有 `.name`（识别文本）、`.x/.y/.width/.height`（像素）、置信度，结果按 y 排序。匹配语义由 `find_boxes_by_name()` 决定，**两种写法行为完全不同**：

| 写法 | 语义 | 骨架中的用例 |
|---|---|---|
| `match="培养"`（str） | **精确相等** `name == box.name` | `in_echo_detail`、`find_add_mat`、`confirm_enhance`、`confirm_enhance_available` |
| `match=re.compile(...)`（Pattern） | **子串搜索** `re.search` | `is_material_shortage`、`handle_dialogs`、`LEVEL_RE` |

影响：

- 精确匹配对 OCR 多一个空格、繁体字、全角符号都直接失配。参考实现同样用 `match='培养'` 且能跑通，说明这些文案实测是干净的；但**新引入的「阶段放入」「强化」尚未实机验证**，且繁体（`培養`/`階段放入`/`強化`）必然失配。
- 正则子串匹配在 `DIALOG_BOX` 这么大的区域里过宽：`NOT_ENOUGH_RE = (不足|材料|贝币)` 会命中强化面板里正常的「材料」标签，**使"材料不足"判定长期为真**。
- `click(hit)` 传入 Box 列表时，`click_box()` 只取 `box[0]`（排序后最靠上的那个），多命中时可能点错元素。

### 4.3 等级解析（最脆弱的一环）

```python
LEVEL_RE = re.compile(r"(\d{1,2})")

@staticmethod
def _parse_level(texts):
    nums = [int(m.group(1)) for t in texts or [] if (m := LEVEL_RE.search(t.name))]
    return max(nums) if nums else None

def read_level(self, box, retries=3):
    for _ in range(retries):
        level = self._parse_level(self.ocr(*box))
        if level is not None: return level   # "读到即返回"
        self.next_frame()
    return None
```

四个问题：

1. **`max` 与文档意图相反**。模块 02 写"取最大值以避开分母"，但等级若显示为 `Lv.1/25`，`\d{1,2}` 会同时抓到 `1` 和 `25`，`max` 取的**恰好是分母（等级上限 25）**。结果：任何 x ≤ 25 都判定"已达标"→ 全部 skip。
2. **`\d{1,2}` 会把 3 位数截断成 2 位**：材料数量 `999` → `99`；若区域内混入材料数，`max` 取 99。
3. 每帧只在每个 Box 里取**第一个**匹配（`search` 而非 `findall`），"等级 12 / 上限 25" 这种同一文本框里的多数字会被漏掉。
4. `read_level` 名为"多帧投票"，实际是**读到第一个非 None 就返回**，单帧误读直接扩散；且无 0–25 合理性校验。

### 4.4 配置与运行期数据

```python
self.default_config.update({
    "目标等级": 15, "允许溢出": True, "达到目标后上锁": False,
    "材料耗尽时暂停": True, "单件超时(秒)": 90, "最大处理数量": 200,
})
self.config_type["目标等级"] = {"type":"drop_down", "options": list(range(1,26))}
```

- `self.config` 是框架 `Config` 实例（按类名持久化为 `configs/*.json`），`.get()` 取值；`run()` 里统一 `int(...)` 包了一层，因此 `options` 为 int 还是被 GUI 转成 str 都能工作 —— R10 的实际风险比文档估计的小。
- `config_type` 的 `drop_down` 写法与现有任务一致（`EnhanceEchoTask` / `FarmEchoTask` 同款），框架会据此自动生成 GUI 面板。
- `info_set()` 只写 GUI 展示计数器（`已完成` / `已失败` / `结束原因`），**不持久化**；断点续跑完全依赖游戏内排序，不依赖这些计数器。

## 5. 升级规则与限制

### 5.1 游戏侧规则（方案文档口径）

| 规则 | 内容 |
|---|---|
| 目标等级 | x ∈ [1, 25]，运行期由下拉框指定 |
| 投料粒度 | 「阶段放入」每点一次投一档材料；方案按 5/10/15/20/25 档位理解 |
| 达标判据 | 强化面板的**预览等级** ≥ x 即停（不看经验表） |
| 溢出 | 材料粒度固定，可能超过 x；默认"接受最近可达等级并告警" |
| 稀有度上限 | 文档承认"已达稀有度等级上限"会表现为按钮变灰/等级不变，但**代码未建模星级与上限的映射** |
| 资源 | 消耗经验材料 + 贝币；不足应正常结束并通知，不抛异常 |
| 调谐 | 必须**关闭同步调谐**，省调谐器、避开「调谐成功」弹窗 |
| 前置 | 游戏语言 zh_CN/zh_TW、背包声骸页预筛并按等级升序、开启「阶段放入」、热键 `b`/`esc`/`c` |

### 5.2 工程侧硬限制

| 常量/配置 | 值 | 作用 | 实际生效情况 |
|---|---|---|---|
| `MAX_BATCH` | 8 | 单件最多投料轮数 | ✅ 生效，但循环内 `preview is None` 时 `continue` 仍会继续点，可能灌满材料 |
| `MAX_RETRY` | 3 | 连续失败保护 | ⚠️ 条件等价于 `done_count == 0`，不是"连续" |
| `最大处理数量` | 200 | 主循环上限 `done + fail < limit` | ⚠️ **skip 不计入**，全 skip 时可无限循环 |
| `单件超时(秒)` | 90 | 防卡死 | ❌ 只在 `process_one` 返回后打日志，不中断 |
| `允许溢出` | True | 控制是否接受超 x | ❌ 配置项定义但从未被读取 |
| `supported_languages` | zh_CN / zh_TW | 语言范围 | ❌ 所有 OCR 文案仅简体，繁体全失配 |

### 5.3 终止条件（3 个 + 1 个计数上限）

`level is None`（读不到等级）/ `level >= target`（队列清空）/ `result == no_material`（资源耗尽）/ `done+fail >= limit`。注意判定**顺序**：`no_material` 排在最后，若资源耗尽同时首格已达标，会报"全部达到目标等级"，原因归类不准。

## 6. 文档与代码的事实性冲突（本次分析新增）

方案文档自身已登记 R1–R10。以下 5 项是文档描述与代码实际不一致、且尚未被登记的部分：

| # | 文档/注释声称 | 代码实际 | 后果 |
|---|---|---|---|
| G1 | 模块 04「投料达标后执行强化」；模块 01「列表页 ↔ 强化页往返」 | **`TRAIN_BTN_BOX` 只在 `in_echo_detail()` 里当探针，全文没有任何一处点击「培养」** | 从背包页进不了强化面板 → `confirm_enhance_available()` 找不到「阶段放入/强化」→ 每件都返回 `skip`，`enhance_to`/`confirm_enhance` 整段不可达 |
| G2 | 模块 01「培养按钮在详情页有、列表页没有，能可靠区分状态」 | 参考实现 `esc()` 是**等到「培养」出现**才停，说明它是"已回到背包页"的标志；`back_to_list()` 写成 `if in_echo_detail(): send_key("esc")`，即"已经在背包页就继续 ESC" | 条件写反，最多连按 6 次 ESC 把背包整个退掉；随后 `SORT_BTN`/`FIRST_SLOT` 在非背包页盲点 |
| G3 | 模块 01「`echo_list_marker` 待标定模板」 | `ok_templates/` 中不存在该特征（现有 `echo_enhance`、`echo_locked`、`echo_not_locked`、`echo_enhance_confirm` 等） | 该 `break` 分支恒不成立，`back_to_list` 的 6 次 ESC 一定会走满 |
| G4 | 模块 04「兼容强化 / 强化并调谐」；总体方案「关闭同步调谐」 | 参考实现 `EnhanceEchoTask` L115 明确：若只 OCR 到「强化」就 `raise Exception('强化设置需要开启同步调谐!')` | 两处对用户设置的假设相反；按本功能"关闭调谐"的设定，实际按钮文案是「强化」还是「强化并调谐」需实机确认，否则 `confirm_enhance` 可能永远点不到 |
| G5 | `supported_languages = ["zh_CN","zh_TW"]` | 全部 OCR 文案为简体：`培养`/`阶段放入`/`强化`/`不再提示`/`点击任`/`不足|材料|贝币` | zh_TW 下探针全部失配。参考实现专门列了 `['本次登录不再提示','本次登入不再提示']` 两种写法，本骨架没有 |

另外，上一轮报告已指出的 `PREVIEW_LEVEL_BOX == DETAIL_LEVEL_BOX`（文档登记为 R9）在这里要补一层理解：即使忽略"两框位置不同"，只要它们同值，`enhance_to` 读到的就永远是当前等级，`preview >= target` 恒不成立 → 投料灌满 → 误判"材料不足"终止。它与 G1 叠加后，当前骨架的实际表现是**第一轮就 `skip` 或 `无法读取等级` 退出**。

## 7. 边界情况清单

| # | 场景 | 触发条件 | 当前行为 | 建议 |
|---|---|---|---|---|
| E1 | 等级文本形如 `1/25` | UI 显示"当前/上限" | `max` 取 25 → 判定已达标 → 全部跳过 | 精确正则 `(?:Lv\.?|等级)\s*(\d{1,2})` |
| E2 | 区域内混入材料数 999 | 标定框过大 | 截断成 99 被 `max` 取走 | 收紧框 + 校验 0–25 |
| E3 | 单帧 OCR 误读 | 常见 | 立即返回错误等级，可能误投料或误判完成 | 连续 3 帧取众数 |
| E4 | 目标 x 非 5 的倍数（如 7） | T4 | `允许溢出` 未生效，仅记日志 | 让配置参与达标判定 |
| E5 | x 小于当前等级 | T3 | `process_one` 返回 skip → **但 skip 不计入 limit**，若无 `level>=target` 终止就会空转 | 把 skip 计入循环上限 |
